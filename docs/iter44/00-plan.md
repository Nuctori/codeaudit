## 候选 1（主推）：局部变量 prop 读误伤——阴影守卫范围收窄（已复现）

**实证**（探针）：`int status_ = 200; if (status_ == 200)` ——局部变量读取 → `obj=null attr=status_ root=bare` unknownCalls（InitDeity 全库 92121 裸名未命中的大头，API.g.cs `status_`4373/`headers_`3988/`e`1992/`i`2369）。**机制**：iter41 阴影守卫（`caller.assigned.includes(attr)` 跳过解析 → ?）对 **prop 读**不适用——**读取局部变量不执行用户代码**（与参数读取同论证，参数读取已判纯）。

**修复**：裸名 prop 读 + assigned 遮蔽 → **判纯**（非 ?）。调用形态遮蔽（`const Math = evil()` 后调用）**维持 ?**（iter41 假纯修复不回退）。

**最小性**：不加新表/新通道——只收窄既有守卫的适用面（prop=true 分支豁免 assigned 检查）。无新机制。

## 候选 2：System 枚举读取判纯（数据表 vs 泛化，请裁决）

**实证**：`StringComparison.Ordinal`（RMA 86 次）、`TaskStatus`（1187）、`BindingFlags`（570）——obj 非项目类 → 效应表 miss → ?。iter42 候选3 只修了项目 enum（GameState.Menu → PURE）。

**方案 A（数据表）**：System 枚举名白名单（StringComparison/BindingFlags/TaskStatus/AttributeTargets…）→ prop 读判纯——B1 同族数据债，人工维护。
**方案 B（机制）**：C# 枚举读取无条件判纯——**假纯风险**：obj 名撞项目类/插件类（编译错？C# 静态类型：`StringComparison.Ordinal` 若 StringComparison 不是枚举则编译不过——但工具无类型系统，无法区分"枚举读取"与"类属性读取"）→ B 方案不可行（除非项目类优先已覆盖）。
**最小性裁决**：A 是数据债（与 B1 合并），B 是危险泛化——请评审裁决 A 的边界（白名单 vs 命名空间前缀规则）。

## 候选 3：`<unresolved>` 形态（7.9%，13575 站点）

**现象**：flattenCallTarget 失败形态（obj=null attr=`<unresolved>`）。**待定位**：提取侧（callOf）对不可拍平调用形态的兜底。**最小性**：若为已知不可拍平形态（`factory()()`/`d[k]()`）→ 设计诚实，维持；若为可解析形态漏网 → 修。请评审裁决是否需要本轮定位（成本 vs 收益）。
