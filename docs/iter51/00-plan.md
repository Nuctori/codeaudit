## 二、审计议题

1. **信息展示合理性**：
   - 各视图是否有冗余/缺失？排序键是否与视图语义匹配？
   - 量纲排序（callers/深度/复杂度/读者数/影响面）各自独立是否正确？有无该排序未排序的视图？
   - 数字展示是否误导（如 density 仍在 HTML 输出但已非判据）？
2. **代码质量影响排序**：
   - 「先改哪个」的排序：callers（被最多人调）vs 传播深度（长链）vs 复杂度 vs 桥/割点——哪个量纲真正回答「质量影响最大」？
   - 各量纲排序之间有无冲突（同一 chunk 在不同视图位置悬殊）？
   - 是否缺「组合视角」（如 深度 × 复杂度 的交叉）——但量纲不混合纪律下如何呈现？
3. **消费面**：每个视图的真实读者（开发者/AI/CI）与动作语义是否明确？

## 三、审计视角（独立 fresh-context，只读）

1. **形式逻辑/数学家**：展示的数学正确性——排序键语义、量纲独立性、数字误导、极小性（死字段/冗余视图）
2. **Jeff Dean 工程视角**：展示的工程合理性——每个视图的成本/价值、读者动作、排序的工程意义
3. **用户/产品视角**：信息展示的直观性——「看这份报告能否直接知道先改什么」

## 四、验收

- 审计发现 → 当轮修复（或记录为有意取舍）→ 验证 → 再审一轮 → 直到无实质发现
- 修复不引入新量纲混合；测试网保持绿
