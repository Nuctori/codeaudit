# 641s 卡点网络层独立审查（网络/系统视角）

> 2026-08-12 独立复审。只读验证（netstat/route/arp/ping/tracert/TCP 实测），未改任何配置。
> 视角结论：**641s 是「OS 层 21s 连接超时 × 引擎层每轮 80s 预算」的叠加**；hosts 黑洞已证明无效；根治需一条管理员命令。

## 2. 超时机制分析（核心问题）

### 2.1 OS 层：每次 connect() = 21s（实测 21.09s），不是 80s

- 注册表 `TcpMaxConnectRetransmissions` / `TcpInitialRtt` 均未设置 → Windows 默认：初始 RTO 3s，SYN 重传 2 次 → **3+6+12 = 21s**。
- 实测与理论完全吻合（21,091ms）。每轮 OS connect 失败 = 21s，8 轮仅 ~170s，**解释不了 641s**。
- 附加实测：本机 **loopback 拒绝也固定耗时 ~2.0s**（python 与 PowerShell 双工具交叉验证 127.0.0.1/127.0.0.2 × 10080/9 端口均为 ~2.02s，开放端口 50ms 正常；Winsock 目录无 LSP，疑为安全软件 WFP callout）。这是本机系统特性，影响一切「被拒绝」的连接速度。

### 2.2 引擎层：80s/轮 的构成（无法直接取证，工程推断）

- 641s ÷ 8 轮 ≈ 80s/轮。TcpProtobuf 在 Unity China 2022.3.62f3c1 **引擎 native 层**（iter37 已穷举 managed dll，无源码、无配置开关）。
- 两种可能构成：
  1. 引擎对每次尝试设 80s 独立超时，异步 connect 只在自设期限到点才检查结果（OS 21s 就失败也不提前处理）；
  2. 引擎每轮内部做多次 OS connect（21s × ~4 ≈ 84s ≈ 80s）。
- 无论哪种：**只要 OS 层 connect 能在毫秒级以非超时错误返回（10061 拒绝 / 10013 拒绝访问），引擎的 80s 预算就会塌缩**。7/25「网络快速失败 → 总耗时 6.3s」是这一推论的直接证据。

### 2.3 为什么 ICMP「host unreachable」不能加速 TCP

- 路由（192.168.1.2）对 ICMP echo 报 unreachable，但 TCP SYN 仍等到 21s 超时。原因：路由对 ICMP 不可达生成做了限速（常见默认 1pps）或对 TCP 不生成；首个 SYN 的 ICMP 即使返回，Windows 重传的 SYN 得不到响应，连接仍按重传序列走到 21s。**结论：指望 ICMP 快速失败不可靠，必须在本机做拦截。**

### 2.4 已验证无效的拦截层（避免重走弯路）

| 方案 | 验证结果 |
| --- | --- |
| **hosts 文件 `127.0.0.1 192.168.1.209`**（已存在） | **无效**。IP 字面量绕过 DNS/hosts 解析。实测：.NET/python 用 "192.168.1.209" 直连 → 21s 真实网络超时，根本没走 loopback。迭代 37 文档同样确认此点 |
| WinINET 代理 127.0.0.1:7890 | 无效。裸 TCP（TcpClient/Socket）不经过 WinINET，WinHTTP 也是直连 |

## 3. 可执行的快速失败方案（按推荐排序）

### 方案 A（推荐，管理员）：路由黑洞 → loopback（10061 秒拒）

原理：给 192.168.1.209 加一条指向 loopback 的主机路由，TCP 连接落 127.0.0.1:10080 → 无监听 → RST/拒绝（实测本机 ~2s 内返回 10061），不再碰真实网络。

```bat
:: 管理员 CMD 执行（持久化，重启仍生效）
route -p add 192.168.1.209 mask 255.255.255.255 127.0.0.1

:: 立即生效的等价写法
netsh interface ipv4 add route prefix=192.168.1.209/32 interface=1 nexthop=127.0.0.1

:: 回滚（服务器恢复时）
route delete 192.168.1.209 mask 255.255.255.255 127.0.0.1
netsh interface ipv4 delete route prefix=192.168.1.209/32 interface=1 nexthop=127.0.0.1
```

- 预期：每轮从 ~80s → ~2s，8 轮 ≈ 16s（641s → ~16s）。
- 已验证前提：`route add` / `netsh interface ipv4 add route` 非提权均报「请求的操作需要提升（作为管理员运行）」exit=1（本机实测）；本机 10080 无监听（netstat 空）。
- 风险：若将来本机某服务监听 10080，连接会连到它；回滚命令已给出。

### 方案 B（管理员）：Windows 防火墙出站拦截（10013 即刻失败）

原理：WFP ALE_AUTH_CONNECT 层 block → connect() 在发 SYN 前被拒绝，应用收到 WSAEACCES(10013)，**无需等待任何网络超时**。

```bat
:: 管理员 CMD 执行
netsh advfirewall firewall add rule name="blackhole-192.168.1.209" dir=out remoteip=192.168.1.209/32 action=block

:: 回滚
netsh advfirewall firewall delete rule name="blackhole-192.168.1.209"
```

- 预期：每轮 <1s（WFP 拒绝即时；本机 loopback 2s 延迟不影响此路径）。
- 已验证前提：`netsh advfirewall set ...` 非提权报「请求的操作需要提升」exit=1（本机实测）。
- 风险：机制（block → 应用即刻收到错误）基于 WFP 语义，非提权无法实测本机行为；若引擎把 10013 也当可重试错误，效果等同方案 A 的 ~2s/轮，仍远优于 641s。

### 方案 C（免管理员，兜底）：物理断网/禁用本机所有网卡

原理：无活动接口 → 无路由 → connect() 立即 WSAENETUNREACH(10051)。

- 操作：Windows 网络托盘「断开」无线/拔网线（无需管理员）。`Disable-NetAdapter` 需要管理员，不适用。
- 预期：每轮 <1s。但注意本机有 Wintun VPN，若底层网络断开后隧道仍存默认路由，可能仍超时——实测验证后才能确认；batchmode 测试本身不需要网络，此方案不损失功能。
- 风险：影响其他联网操作；VPN 残余路由不确定性。仅作兜底。

### 明确不可行（非管理员）清单

- hosts 拦截：**已实测无效**（IP 字面量绕过）。
- 代理/WinHTTP：裸 TCP 不走。
- 修改注册表 TCP 参数（TcpMaxConnectRetransmissions=0）：HKLM 需管理员，且只把 21s 降到 ~3s，仍不达标。
- 结论：**非管理员无有效快速失败手段**；最省事路径 = 一次管理员运行方案 A 或 B。

## 4. 残余风险

1. 引擎对 10061/10013 是否同样重试 8-10 次未知（native 无源码）；即使重试，每轮 ≤2s，总耗时 ≤20s，量级上不再是阻塞。
2. 方案 B 的即时失败行为无法在非提权下实测（理论依据：WFP ALE block 语义）。
3. 本机 loopback 拒绝 ~2s 的系统级延迟来源未定位（Winsock 目录无 LSP；tasklist 无常见 AV 进程；疑为安全软件 WFP callout），只影响方案 A 的速度上限，不影响方案 B。
4. 192.168.1.209 若恢复在线，方案 A/B 会持续黑洞该地址——回滚命令已给出；建议测试跑完后回滚或保留并记录。
5. 641s 的 80s/轮构成（引擎 80s 定时 vs 4×21s 组合）未能直接取证——但不影响任何方案有效性，因为所有方案都绕开 OS 21s 超时本身。

## 5. 结论一句话

**641s 可 30-300× 压缩：管理员跑一次 `route -p add 192.168.1.209 mask 255.255.255.255 127.0.0.1`（方案 A）或防火墙出站 block（方案 B），引擎每轮从 80s 塌缩到 ~2s；hosts 黑洞、代理、VPN 均已实测排除。**
